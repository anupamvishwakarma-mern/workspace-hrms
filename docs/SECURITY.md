# Security review (Phase 7)

Scope: the API, web admin and mobile client in this repository as of Phase 7. This is a **code and test review by the developer of the system, not an independent penetration test.** Treat it as a checklist and a record of decisions, and commission an external test before handling real employee data at scale.

## Findings fixed in Phase 7

1. **Leave approve/reject had no route-level permission guard** (found by the new authorization matrix). The service checked permissions, but only after looking the request up, so a user with no review rights got 404 for a missing id and 403 for an existing one (an existence oracle inside their own company), and validation errors came before authorization. Fixed: route guard added and the service checks permission first.
2. **Two updates were not tenant-filtered** (found by the new query guard): the resulting-event link on an attendance exception, and email-outbox status updates. Both filtered by a unique `_id` so they were not exploitable, but they now include `tenantId` as defence in depth.
3. **High-severity advisory in zod** (memory exhaustion on oversized constrained collections) in the API, mobile and web: upgraded to a patched version. The API rejects bodies over 100 kB regardless.
4. **Vulnerable dev tooling** (vitest/vite/tinypool, including critical advisories that apply when the test UI server runs): upgraded.
5. **Production config hardening**: distinct token secrets, https-only origins, API docs off by default, unhandled promise rejections now crash and restart instead of leaving a half-working process.
6. Employee code generation retries on collisions (Phase 6) and the document-upload CSP gap (Phase 6) were found by browser testing.

## Residual risks and accepted trade-offs

- **`pnpm audit` still reports:** `node-forge` and a `zod` copy inside Expo's CLI (developer tooling, not part of the shipped app; no patched node-forge exists yet), and `dicer` / `fast-xml-parser` inside `s3rver` (a test-only storage emulator). None is installed in the production images (`pnpm deploy --prod`). Re-run the audit regularly; the mobile bundle's own dependency tree should be audited again before store release.
- **CSP `script-src 'unsafe-inline'` in the web app.** Next injects inline bootstrap scripts; a nonce-based policy needs per-request rendering and was judged too invasive for this phase. Mitigations: no third-party scripts, no `unsafe-eval` in production, `connect-src` limited to self and the storage origin, no user-supplied HTML is ever rendered (React escaping; no `dangerouslySetInnerHTML`), tokens are not readable by script (refresh) or short-lived and in memory (access).
- **Account lockout can be abused to lock someone out** (5 bad attempts by anyone). Chosen over unlimited guessing; it expires after `LOCKOUT_MINUTES`. Per-IP limits help but are per process.
- **Rate limits are in-memory per instance** (see DEPLOYMENT.md).
- **GPS does not prove presence.** Coordinates can be faked on a rooted/jailbroken device. The app records mock-location signals and accuracy, flags exceptions for human review, and the review process is the control; the documentation never claims GPS alone prevents fraud.
- **No MFA, no SSO, no password-breach checks.** Passwords need 10+ characters with letters and digits.
- **No malware scanning of uploaded documents** and no content sniffing beyond the declared type and size check. Files are served as attachments from a different origin (the bucket).
- **No tenant deletion / employee erasure tooling** (GDPR-style requests need manual work). Audit entries are retained.
- **Email delivery and S3/Expo behaviour** were tested against local emulators, not real providers.
- **The Docker images were not built** in this environment.
- **Mobile app has not been run on a physical device** (see MOBILE.md), so permission prompts, secure storage and background behaviour are unverified.

## Added with the HR pages

- Payroll, letters and handbook are tenant-scoped like everything else (every query carries `tenantId`; out-of-scope ids return 404) and covered by the authorization-matrix test.
- Payslips are visible to an employee only for their own published run; HR cannot edit their own salary structure; published runs and structure versions are immutable; generation, publishing, issuing and revoking are audited.
- Letter and handbook text is plain text and never rendered as HTML on web or mobile.
- Team-today returns statuses only (no coordinates or photos) and is scoped server-side to direct reports for managers.
- Residual risk: pay data is sensitive and is stored unencrypted at the application level (database-at-rest encryption is a deployment concern); there is no payroll maker-checker approval step.

## Reporting

Report vulnerabilities privately to the maintainers of your deployment. Do not open public issues with exploit details.


## Customer database credentials

Encrypted with AES-256-GCM (versioned key ring), never returned or logged, visible to no HR role; only the company owner can replace them (re-authentication, audited). SSRF protections apply to every customer host. See DATABASE_HOSTING.md.
